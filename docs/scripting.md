# Scripting reference

A **script** is a Rhai program that composes several `api_call`s into one model-usable answer —
Level 2 of the three levels of use described in the [README](../README.md). This is the reference
for writing one: every script-callable function, grouped by purpose, with its signature and a
realistic example. It is generated by reading `src/script/**` directly, so treat it as the source
of truth alongside that code; if the two ever disagree, the code wins.

The function list below was cross-checked against `src/script/engine_probe.golden` (the golden
file `src/script/engine.rs`'s `registered_functions_match_the_committed_golden_file` test compares
against) — as of this writing they agree exactly; that test is what will tell you if they drift.

## What a script is, mechanically

A script is one Rhai expression (or statement sequence) stored as plain text
(`model::ScriptDef::source`), exposed as an MCP tool exactly like an `api_call` is. It declares:

- **`params`** — the same `Param` shape an `api_call` uses (name, type, required, default, enum
  values), except every script param's location is `Local`: it is bound into the script's Rhai
  scope as a plain variable and never placed into an HTTP request. This is why `script_params` (the
  DB table) has no `location`, `fixed_value` or `body_path` columns — those describe *where in a
  request* a value lands, which is meaningless for a script input.
- **`callable`** — a map from the alias a script uses inside `api(alias, ...)` to the `api_call`
  slug it actually names. This is I1's declarative half: a script can only ever reach the api_calls
  it declared here, intersected with what the endpoint that exposes it actually selects
  (`EndpointPlan::callable_by`). An alias absent from this map, or naming an api_call the endpoint
  doesn't expose, is not a permissions error the script can catch and route around — it can never
  reach `dispatch` at all.
- **`budgets`** — a script's own opinion on `max_calls`/`max_bytes`/`wall_clock`/`max_pages`/
  `max_concurrency`, always folded with its endpoint's via `Budgets::fold` (element-wise `min`), so
  a script can only *narrow* what its endpoint allows, never widen it (I6).

The engine itself (`Engine::new_raw()`, `src/script/engine.rs`) is hand-assembled rather than
`rhai::StandardPackage`, with hard resource limits, `eval`/`import` disabled, and `print`/`debug`
routed only to `tracing::debug!` (never into a model's context or a run's audit body). See
[What's deliberately absent](#whats-deliberately-absent-and-why) for the full list and why.

## Calling APIs: `api`, `api_many`, `api_try`

These are the **only** three functions that can ever reach HTTP, and even they don't directly —
each marshals its arguments, sends a message across an internal channel to the async side, and
blocks for a JSON reply. The actual I1 enforcement (checking the alias against what this script
declared and this endpoint exposes) happens on that async side, in `runtime::dispatch::resolve` —
one place to audit, and it's the same place that resolves the call for every other caller (the
CLI, a directly-invoked tool), not a second check that could drift from it.

### Why `api`, not `call`

Rhai's interpreter hard-reserves the name `call` as `KEYWORD_FN_PTR_CALL`: it always means "invoke
this function pointer" inside `make_function_call`, so `engine.register_fn("call", ...)` would be
**silently shadowed** — the interpreter would coerce the first argument as a function pointer
instead of ever reaching a registered closure, with no error at registration time or call time.
This project got bitten by exactly this class of bug once already (a sibling project, per
`src/script/bindings.rs`'s own comment, renamed its equivalent binding to `exec` after hitting it),
so the bindings here are named `api`/`api_many`/`api_try` from the start. The same interpreter
special-casing also rules out `fn`, `this`, `type_of`, `is_def_fn`, `is_def_var`, `Fn`, and `curry`
as binding names — none of these are legal to register either, for the same reason.

### `api(name, args)` — one call, throws on failure

```rhai
let item = api("get", #{ "id": "3" });
```

- `name` — the alias declared in this script's `callable` map.
- `args` — a Rhai object map (`#{...}`) of the target api_call's own parameters.
- Returns the api_call's projected value directly on success.
- **Throws a catchable exception** (`try`/`catch`-able) carrying the failure message on any
  per-item failure. This is the one function of the three that throws — reach for it when a single
  failed call should abort the script, exactly like an unhandled exception in any other language.

### `api_many(name, args_list)` — a batch, never throws

```rhai
let results = api_many("get", [#{ "id": "1" }, #{ "id": "2" }, #{ "id": "3" }]);
```

- `args_list` — a Rhai array of argument maps, sent as **one batch** through the shared
  budget/concurrency machinery (`runtime::partial::run_batch`) rather than as a loop of individual
  `api()` calls — this is what lets several calls share one budget reservation and run concurrently
  under the endpoint's `max_concurrency`.
- Returns an array of exactly `args_list.len()` per-item result objects, always in **input order**
  (I7) regardless of completion order — see [Result shape](#the-per-item-result-shape) below.
- **Never throws for a per-item outcome.** A failed item is a result object with `ok: false`, not
  an exception — the whole point of `api_many` is that one bad item doesn't abort the batch.
- Capped at 500 items per call (`script::bridge::MAX_BATCH`) — a script-authoring limit, refused
  outright (a catchable error) rather than silently truncated.

### `api_try(name, args)` — one call, never throws

```rhai
let r = api_try("get", #{ "id": "999" });
if r.ok {
    print(r.value);
} else if r.error.kind == "http_status" {
    // handle a 404/500/etc. from the upstream without a try/catch block
}
```

Identical to `api` in every way except it never throws: it always returns the single per-item
result object `api_many` would have put at index 0 for a one-item batch. Use this when you want to
branch on a failure inline rather than wrap the call in `try`/`catch`.

### The per-item result shape

Every element `api_many` returns, and everything `api_try` returns, has this shape:

```json
{ "ok": true,  "index": 0, "value": <the projected result> }
{ "ok": false, "index": 1, "error": { "kind": "http_status", "message": "...", "status": 404, "reason": "Not Found", "detail": "..." } }
```

- **`ok`** — whether this item succeeded.
- **`index`** — this item's position in the input list (or `0` for `api`/`api_try`'s one-item
  batch). Always present, `ok` or not.
- **`value`** — present iff `ok` is `true`: the api_call's projected result, exactly as an MCP
  caller would see it.
- **`error`** — present iff `ok` is `false`. It is an **object**, not a string, always carrying a
  `kind` tag (plus `message`, and extra fields for some kinds) so a script can branch on the
  failure category instead of pattern-matching prose. This is the same tagged shape
  `runtime::dispatch::DispatchError`'s `Serialize` impl produces and a run's own persisted
  `errors[]` column uses — a script's view of a failure and the audit record of it can never
  disagree. `error.kind` is one of:

  | `kind` | Meaning |
  |---|---|
  | `not_declared` | The alias isn't in this script's `callable` map, or the endpoint doesn't expose the api_call it names — I1 refusing the call before it ever reaches HTTP. |
  | `not_an_api_call` | The name resolves to a script, not an api_call (only relevant off the direct-invocation path; a script's own `callable` map can never name another script). |
  | `args` | The arguments failed `schema::bind_args` — a required param missing, a type mismatch, an unknown key, or a value outside `enum_values`. |
  | `bind` | The bound arguments couldn't be assembled into a request (I3's containment check, a header outside the allowlist, a body-assignment failure, ...). |
  | `send` | *This one request's own* transport failure: DNS/SSRF guard rejection, connection failure, **this request's own timeout** (either its api_call/service's configured `timeout_ms`, or the run's overall deadline expiring while it was in flight), or **this request's own pagination page-cap trip**. Still an ordinary, catchable per-item error — see the note below for when it isn't. |
  | `client` | Building the upstream HTTP client for this service failed. |
  | `http_status` | The upstream responded with a non-2xx status. Carries `status` (u16), `reason`, and a redacted, truncated `detail` excerpt of the upstream's own error body — often enough for a script (or the model reading the script's output) to see *why* and adjust. |
  | `response_not_json` | The upstream's body didn't parse as JSON where the api_call expected it to. |
  | `projection` | The api_call's declared projection failed against the actual response shape (a `Cardinality::One` field matched zero or more than one node, or a coercion failed). |
  | `budget_exceeded` | This item was never attempted (the whole batch's call reservation was refused up front, before any HTTP call in the batch was made), or it ran but was excluded by the post-hoc, index-order bytes/pages commit (see [Budgets](#budgets-and-what-a-script-sees-when-one-trips)). Carries an `axis` field (`"calls"`, `"bytes"`, `"wall_clock"`, or `"pages"`) naming which one. **Never** how an individual request's own timeout or page-cap trip is reported — those are `send`, above. |

  A `send`-kind timeout or page-cap trip is internally tagged with the same budget axis a
  genuine `budget_exceeded` would use (`runtime::dispatch::DispatchError::budget_trip`), but only
  to decide the *batch's* overall status — never to change what an individual item looks like.
  The one place this becomes visible to a script: if **every** item in one `api_many`/`api_try`
  call times out (a dead upstream, say), the whole call is escalated to termination rather than
  returned as an array of `send` errors — see [Budgets](#budgets-and-what-a-script-sees-when-one-trips).
  A batch with at least one success alongside timed-out items still returns the timeouts as
  ordinary catchable `send` entries.

## Time: `execution_start()` vs. `now()`

```rhai
let cutoff = execution_start() - days(7);   // reproducible: same every time this run replays
let stamp  = now();                          // the live wall clock — moves every time you call it
```

Two clock functions exist, and the choice between them is the whole reason this section is
written the way it is:

- **`execution_start()`** returns a single `Timestamp`, captured once at the very start of the run
  (`BudgetMeter::new`) and constant for every call within it. A script built entirely on
  `execution_start()` is **reproducible**: given the same upstream responses and the same recorded
  start time, it produces the same output — and both of those are exactly what a run's audit
  record (`runs.definition_snapshot`, the recorded `execution_start`) preserves, so such a script
  is replayable after the fact.
- **`now()`** is the real, moving wall clock. It exists because scripts need real date logic to be
  useful for transformation (computing "is this stale", formatting a display date, and so on), but
  calling it means the script's output can differ between two runs even given identical upstream
  data — that trade-off is deliberate, and it stays visible **in the script's own source** rather
  than being hidden inside the engine. Reach for `execution_start()` by default; reach for `now()`
  only when you specifically need the real current instant and are consciously giving up
  replayability.

This is invariant I7 restated: the crate's *mechanical* determinism (stable iteration order,
fan-out results in input order, budgets committed in index order) is unconditional and unaffected
by either function — only a script's own *output* becomes non-reproducible, and only if it calls
`now()`.

Neither function is ever named `timestamp()` — that name, along with `rhai::packages::
BasicTimePackage` it would come from, is deliberately excluded from the engine entirely (see
[What's deliberately absent](#whats-deliberately-absent-and-why)). `Timestamp::unix_seconds()` is
spelled that way, not `.timestamp()`, for the same reason.

## The `Timestamp` and `Span` types

`Timestamp` wraps an instant (UTC); `Span` wraps a duration. Neither is a bare integer or an RFC
3339 string passed around by convention — arithmetic and comparison are real operators, not string
munging.

**Constructing a `Timestamp`:**

| Function | Signature | Notes |
|---|---|---|
| `parse_timestamp(s)` | `(String) -> Timestamp` | Parses RFC 3339 (e.g. `"2024-01-01T00:00:00Z"`). Throws a catchable error naming the input on failure. |
| `parse_date(s, fmt)` | `(String, String) -> Timestamp` | Parses `s` against a `strftime`-style `fmt` (e.g. `"%Y-%m-%d"`, `"%d/%m/%Y"`). Tries a full date+time, an offset-aware date+time, then a date-only match at midnight UTC. Throws on no match or an invalid format string — never panics. |
| `is_valid_timestamp(s)` | `(String) -> bool` | `true` iff `s` is valid RFC 3339 — for validating without throwing. |
| `is_valid_date(s, fmt)` | `(String, String) -> bool` | As above, for `parse_date`'s format. |
| `execution_start()` | `() -> Timestamp` | See [above](#time-execution_start-vs-now). |
| `now()` | `() -> Timestamp` | See [above](#time-execution_start-vs-now). |

**`Timestamp` methods:**

| Method | Returns | Notes |
|---|---|---|
| `.to_rfc3339()` | `String` | |
| `.format(fmt)` | `String` | `strftime`-style. Throws a catchable error on an invalid format string rather than panicking (chrono's own `.format().to_string()` can panic on a bad specifier; this validates first). |
| `.year()` / `.month()` / `.day()` / `.hour()` / `.minute()` / `.second()` | `int` | |
| `.weekday()` | `String` | e.g. `"Mon"`. |
| `.unix_seconds()` | `int` | Epoch seconds. Not spelled `.timestamp()` — see above. |
| `.is_between(start, end)` | `bool` | Inclusive both ends. |

**Comparison:** `==`, `!=`, `<`, `<=`, `>`, `>=` are all defined between two `Timestamp`s.

**Arithmetic:** `Timestamp + Span -> Timestamp`, `Timestamp - Span -> Timestamp`, and
`Timestamp - Timestamp -> Span`. All three throw a catchable error on overflow instead of
wrapping or panicking.

**Constructing a `Span`:** `days(n)`, `hours(n)`, `minutes(n)`, `seconds(n)`, `millis(n)` — each
`(int) -> Span`, throwing a catchable error if `n` is out of range rather than silently wrapping.

**`Span` methods:** `.whole_days()`, `.whole_hours()`, `.whole_minutes()`, `.whole_seconds()`,
`.whole_millis()` — all `() -> int`. `Span + Span` and `Span - Span` are also defined, throwing on
overflow.

```rhai
let created = parse_timestamp(item.created_at);
let age = now() - created;
if age.whole_days() > 30 {
    // ...
}
```

## JSON and YAML

| Function | Signature |
|---|---|
| `json_parse(s)` | `(String) -> Dynamic`, throws a catchable error naming the line/column on invalid JSON |
| `json_stringify(v)` | `(Dynamic) -> String`, compact |
| `json_stringify_pretty(v)` | `(Dynamic) -> String`, indented |
| `yaml_parse(s)` | `(String) -> Dynamic`, throws a catchable error naming the line/column when the underlying parser reports one |
| `yaml_stringify(v)` | `(Dynamic) -> String` |

There is no `yaml_stringify_pretty`: unlike JSON, YAML's block style is already the only
stringification mode this crate's YAML library produces — there is no denser alternative for
"pretty" to mean, so a second name would just be a synonym.

All five route through the same `Dynamic <-> serde_json::Value` conversion the whole script layer
uses (`script::marshal`), so a whole-number literal too large for `i64` is refused rather than
silently rounded — the same "no lossless-precision loss" rule the HTTP boundary applies.

## Regular expressions

| Function | Signature | Notes |
|---|---|---|
| `regex_is_match(pattern, text)` | `(String, String) -> bool` | |
| `regex_find(pattern, text)` | `(String, String) -> String \| ()` | `()` (unit) on no match, never an error. |
| `regex_captures(pattern, text)` | `(String, String) -> Map \| ()` | Keys `"0"`, `"1"`, ... for numbered groups plus each named group's own name. `()` on no match. |
| `regex_replace(pattern, text, replacement)` | `(String, String, String) -> String` | First match only. |
| `regex_replace_all(pattern, text, replacement)` | `(String, String, String) -> String` | Every match. |
| `regex_split(pattern, text)` | `(String, String) -> Array` | |

Patterns compile against the `regex` crate (linear-time, no backtracking — a pathological pattern
cannot itself cause exponential blowup the way a backtracking engine's can; the engine's own
operation/wall-clock limits remain the real backstop against a huge *input*). Compiled patterns
are cached for the lifetime of one run, so calling the same pattern in a loop compiles it exactly
once. An invalid pattern is a catchable error naming the problem, never a panic.

```rhai
let m = regex_captures("(?P<year>\\d{4})-(?P<month>\\d{2})", item.date);
if m != () {
    print(`${m.year}/${m.month}`);
}
```

| Function | Signature | Notes |
|---|---|---|

| `parse_float_or(s, fallback)` | `(String, float) -> float` | Same. |
| `round_to(x, places)` | `(float, int) -> float` | |
| `clamp(x, lo, hi)` | `(int\|float, ...) -> int\|float` | Registered for both `int` and `float`. Handles `lo > hi` by swapping rather than panicking. |
| `format_thousands(x)` | `(int\|float) -> String` | `1234567` → `"1,234,567"`. |
| `format_precision(x, places)` | `(float, int) -> String` | Fixed decimal places. |

| `safe_slice(s, start, end)` | `(String, int, int) -> String` | Indexes by Unicode scalar (char), never byte offset, so a multi-byte character can never split mid-codepoint. Out-of-range or reversed indices are clamped/swapped, never rejected. |

## What the base engine already gives you

On top of everything above, the engine registers `StandardPackage`'s eight sub-packages **minus**
`BasicTimePackage` (see [below](#whats-deliberately-absent-and-why)): `Core` (language core,
arithmetic, basic strings, iterators, function pointers), `BitField`, `Logic` (`min`/`max`),
`BasicMath` (`floor`/`ceiling`/`round`/`fraction`/trig/`parse_int`/`to_int`/`to_float`/...),
`BasicArray`, `BasicBlob`, `BasicMap`, and `MoreString` (`.contains`/`.ends_with`/`.crop`/
`.make_upper`/...). These are ordinary Rhai — see the
[Rhai language reference](https://rhai.rs/book/) for the full list — mentioned here only so you
know they're present without needing to guess or probe for them.

## Budgets and what a script sees when one trips

An endpoint's (and, folded narrower, a script's own) `Budgets` — `max_calls`, `max_bytes`,
`wall_clock`, `max_pages`, `max_concurrency` — are enforced entirely by the runtime, never by the
script (I6); a script cannot read, raise, or bypass them. What a script author actually
experiences when one trips:

- **`max_calls`** is checked **whole-batch, all-or-nothing**, before any HTTP call in the batch is
  made: if `api_many` asks for more calls than remain, *none* of that batch's items are attempted,
  each coming back as `budget_exceeded`/`axis: "calls"` — never a partial admission that depends on
  interleaving.
- **`max_bytes`/`max_pages`** are checked **after** a batch completes, against the *totals* the
  batch's successful calls actually used, committed in **input-index order** (never completion
  order) — so which item (if any) gets excluded is deterministic (I7) regardless of which upstream
  call happened to answer first. An excluded item's request genuinely went out and is still
  recorded to the audit trail, but its result comes back to the script as `budget_exceeded`, not
  its real value. This is a *batch-total* check — it's separate from a single call's own pagination
  needing more pages than remain for it, which surfaces as an ordinary `send` error instead (see
  the [result shape](#the-per-item-result-shape) table above).
- **`wall_clock`** is two-tiered. An individual call's own timeout — whether from its api_call/
  service's configured `timeout_ms` or from the run's deadline expiring while that one call was in
  flight — is an ordinary, catchable `send` error, exactly like any other per-item failure, *as
  long as at least one other item in the same batch succeeded or failed for a different reason*.
  But once the run's deadline has passed **before** a batch can even start, or every item in one
  batch times out, that escalates to `EvalAltResult::ErrorTerminated` — the **one error class a
  script's `try`/`catch` cannot swallow**. This also fires while a script is parked waiting on an
  `api`/`api_many`/`api_try` reply (not just while Rhai bytecode is actively executing), so a
  script cannot dodge the deadline by blocking on a slow call. Only this escalated case ends the
  run outright; an isolated slow call among otherwise-successful ones is just another value in the
  returned array.

There is also a hard, deterministic operation cap (2,000,000 Rhai operations) enforced regardless
of `wall_clock` — a runaway loop with no I/O in it still terminates.

## What's deliberately absent, and why

| Absent | Why |
|---|---|
| `eval(...)` | Disabled outright (`engine.disable_symbol("eval")`). A script evaluating script-authored strings as code would make every static guarantee about what a definition can do worthless. |
| `import "..."` | Disabled outright, and the engine's module resolver limit is set to zero as belt-and-braces. There is nothing to import — no module ever resolves. |
| `timestamp()`, or anything from `BasicTimePackage` | I7 was originally absolute ("no clock at all"); `execution_start()`/`now()` are the two deliberately separate, explicitly-named doors time now enters through instead. Registering `BasicTimePackage` would reintroduce a wall clock with no visible marker in a script's source, defeating the point of making the reproducibility trade-off visible. A golden test (`engine::tests::registered_functions_match_the_committed_golden_file`) fails if this package is ever added back by accident. |
| Filesystem access | Never registered; `new_raw()` starts with nothing, and this module never adds it. |
| Network access beyond `api`/`api_many`/`api_try` | I1: a script never performs HTTP directly. These three functions are the *only* path from script code to `runtime::dispatch`, and even they only ever reach an api_call the endpoint has already exposed to this script — never an arbitrary URL. |
| `call` as a binding name | Reserved by Rhai's interpreter (`KEYWORD_FN_PTR_CALL`) — see [above](#why-api-not-call). |
| `print`/`debug` reaching a model or the audit log | Both are routed to `tracing::debug!` only, so a script can't use them as a side channel around projection/redaction. |
| Unbounded resources | Every one of operations (2,000,000), call depth (64), expression depth (64), string size (256 KiB), array/map size (10,000 elements), variable count (1,000), function count (200), and interned strings (1,024) has an explicit ceiling. An absent map key errors (`set_fail_on_invalid_map_property`) instead of silently yielding `()`, and undeclared variables are rejected (`set_strict_variables`) — both catch a script bug (or an unexpected upstream shape change) immediately instead of letting it propagate as a wrong answer. |

## A complete example

This is `examples/demo.pack.yaml`'s `item-summary` script, composing two api_calls (I1: only
through their declared aliases) into one answer:

```rhai
let listing = api("list", #{});
let items = listing["items"];
if items.len() == 0 {
    #{ "count": 0, "first": () }
} else {
    let first_id = items[0]["id"];
    let detail = api("get", #{ "id": first_id });
    #{ "count": items.len(), "first": detail }
}
```

Its `callable` map (`get: get-item`, `list: list-items`) is what lets `api("list", ...)` and
`api("get", ...)` resolve at all — try it against `examples/demo.pack.yaml` with:

```bash
api2mcp script run item-summary --endpoint demo
```

## Debugging a failing script

A syntax error, an uncaught exception, a termination (wall-clock or an uncatchable resource limit),
or a panic in the engine all come back as the same shape: a `kind`
(`compile`/`runtime`/`terminated`/`panic`), a `message`, and — when Rhai had a position for it — a
`line`, `column`, and a source snippet with a `^` caret under the offending column. `api2mcp script
run` prints this to stderr; `POST /api/scripts/{slug}/test` returns it in the response body as
`failure`.
